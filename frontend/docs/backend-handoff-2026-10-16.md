# 한성픽 백엔드 연동 전달서

작성: 2026-10-16 KST · 대상 프론트 v1.16.76

저장소 안내: 이 문서의 `dist/`, `tests/`, `package.json`은 모두 `frontend/` 아래 경로입니다. 기존 `backend/` 구현 상태를 이 문서가 판정하지는 않습니다.

이 문서는 **현재 프론트에 구현된 규칙, 백엔드에 필요한 기능, 연동하면서 바꿀 부분**을 나눈 전달서입니다. API 주소·경로·서버 응답 형식은 아직 제공받지 않았으며, 아래 요구사항을 이미 구현된 서버 명세로 간주하면 안 됩니다. 성진님과 합의한 OpenAPI/Swagger 명세가 최종 계약이 됩니다.

## 1. 현재 코드와 최종 점검 결과

- 정적 HTML/CSS/JavaScript ES modules입니다. React/TSX 프로젝트가 아닙니다. `dist/`를 정적 호스팅하며, 서버 코드·DB·API 호출은 아직 없습니다.
- 실제 로그인/가입/소셜 연결/계정 변경/탈퇴, 서버 프로필/북마크 저장, 학교 데이터 및 AI API는 미연결입니다.
- 현재 프로필·북마크는 브라우저 `hsupick-v1`, 둘러보기 허용은 탭의 `hsupick-browse-this-tab`을 사용합니다. **둘러보기 플래그와 입력한 이름은 인증 증거가 아닙니다.**
- `npm run check` 통과: **926개 인메모리 DOM 흐름 검사**, 데이터 경계·세션·가입 입력·이미지 URL·추천 검사. JS 문법 및 `git diff --check` 통과.
- 이번 추가 수정: 트랙 조건 미확인을 ‘무관’으로 설명하던 표시, 같은 ID의 내용이 갱신돼도 원문/이미지 팝업이 이전 상태를 유지하던 문제, 보고 있던 이미지 삭제 후 오래된 확대 화면이 남던 문제. 의미 없는 트랙 문자열(‘트랙’만 있는 값)도 읽기 모델에서 거절합니다. 수정 전 실패·수정 후 통과를 확인했습니다.
- **미검증:** 실제 iPhone/안드로이드/PC 렌더링·키보드·터치, 실서버 HTTP 오류, CORS/쿠키/소셜 콜백, 서버 저장 실패, 실제 네트워크 단절. 이 결과는 자동화된 코드 검사 범위이며 실제 서비스 화면·서버 통합 검증은 별도입니다.

판정: 로컬 화면 체험과 프론트 회귀 검사는 가능하지만, 정식 서비스의 무오류·연동 완료를 보장하는 상태는 아닙니다.

## 2. 그대로 공유해야 할 사용자 입력 규칙

| 항목 | 현재 프론트 규칙 | 서버에서 할 일 |
|---|---|---|
| 이름 | 앞뒤 공백 제거 후 1~30자. 한글 가능 | 가입·프로필 API에서 동일 검사. 공백만 있는 이름 거절 |
| 아이디 | ASCII 영문 대소문자·숫자만, 4~20자. 이메일 형식 강제 없음 | 동일 검사·중복 차단. 대소문자 구분 정책 합의 |
| 비밀번호 | 8~32자, ASCII 영문·숫자·기호 각 1개 이상, 한글·공백 불가 | 동일 검사. 자동 trim/소문자 변환 금지. 비밀번호 원문을 응답·로그·DB에 저장하지 않기 |
| 비밀번호 확인 | 비밀번호와 완전히 일치 | DB 저장 필드가 아님. 요청에 포함할지 합의 |
| 학년 | 1·2·3·4·기타 | 문자열/숫자 enum 변환 합의. 기타를 무조건 4로 저장하지 않기 |
| 1학년 | 1트랙만 필수. 소속 대학·학부·학과 선택. 2·3트랙 불필요 | 다른 학년→1학년 변경 시 2·3트랙 정리 |
| 2·3·4학년·기타 | 1·2트랙 필수, 3트랙만 선택 | 필수 누락·목록 밖 값·중복 선택 거절 |
| 트랙 | 팝업 카탈로그에서 선택. ‘미정’ 없음 | 동일 카탈로그/별칭 매핑 제공. 1/2/3번 슬롯 보존 |
| 관심 분야 | 정해진 8개 중 1~4개 | ID와 개수 검사, 중복 제거 |

트랙은 DB의 **안정적인 ID + 표시명 + 종류(college/department/track)**로 관리하는 것이 연동 제안입니다. 현재 프론트 프로필은 이름 배열을 저장하고, 카탈로그 ID는 배열 위치를 포함해 생성합니다. 따라서 현재 ID를 영구 DB ID로 그대로 확정하지 마세요. 명칭 개편·카탈로그 순서 변경에도 같은 선택을 식별할 매핑이 필요합니다.

현재 선택기는 1트랙에서 모든 학년에게 대학 항목을 허용하며, 1학년의 1트랙만 실제 트랙 항목을 제외합니다. 2·3트랙에는 대학 항목이 없고 학부·학과는 있습니다. **2학년 이상 1트랙에서 대학 선택까지 허용할지**는 서버 검증을 확정하기 전에 함께 결정해야 합니다. 실제 화면·서버 허용 범위가 달라지면 프론트 카탈로그 필터도 바꿉니다.

## 3. 분류는 세 종류를 구분합니다

화면 카테고리와 학생 관심 분야는 서로 다른 데이터입니다. 한글 이름이나 같은 ‘창업’이라는 이유로 같은 enum을 공유하면 안 됩니다.

| 구분 | ID → 표시명 |
|---|---|
| 관심 분야 `category` / 프로필 `interests` | scholarship → 장학·지원, career → 진로·취업, intern → 현장실습, contest → 공모전·대외활동, study → 학습·전공, startup → 창업, wellbeing → 상담·마음건강, culture → 문화·교류 |
| 공지 UI `noticeCategory` | academic → 학사, scholarship → 장학·지원, career → 진로·취업, intern → 현장실습, activity → 비교과, startup → 창업, international → 국제·교류 |
| 비교과 UI `programCategory` | learning → 학습역량강화, counseling → 상담·심리지원, startup → 창업지원, major → 전공역량강화, other → 기타 |

- `all`(전체)·`recommended`(추천)는 조회 필터이지 실제 게시물의 분류값이 아닙니다.
- 알 수 없는 분류는 프론트에서 미분류로 표시합니다. 학교 분류명/서버 enum → 프론트 분류 ID의 매핑표가 필요합니다.
- 현재 게시물의 관심 주제는 `category` 한 개입니다. 서버가 여러 관심 주제를 전달한다면 추천/검색 구조도 수정해야 합니다.
- 카테고리 표시 순서·줄 배치는 프론트 책임입니다. DB 정렬순서에 의존해 화면 순서가 바뀌지 않도록 합니다.

## 4. 목록·상세 데이터 계약

현재 읽기 모델은 `dist/content-contract.js`의 `normalizeContentRecords` / `replaceContentRecords`입니다. 실제 API 호출/페이지네이션 처리가 아닌 **매핑 후 검증 도구**입니다.

| 필드 | 현재 읽기 모델에서 받는 값 | 유의사항 |
|---|---|---|
| id | 영문·숫자·밑줄·하이픈 문자열 1~128자 또는 0 이상의 안전한 정수 | 문자열로 통일. notice/program 전체에서 중복 금지. 서버의 큰 정수는 문자열로 전달 |
| type / title | notice 또는 program / 비어 있지 않은 문자열 | 알려지지 않은 유형은 거절 |
| start / deadline | 실제 존재하는 YYYY-MM-DD, start≤deadline | 현재는 둘 다 필수. 미확인·상시모집·기간 없는 공지는 아래 개선 필요 |
| publishedAt | 실제 게시 등록일 또는 ISO 타임스탬프 | 신청 시작일로 임의 대체 금지. 최근 등록순의 기준 |
| eventAt | 선택 날짜 | 신청 마감과 활동일 구분 |
| grades | 1~4 배열 | `[1,2,3,4]`는 전 학년. null/누락/빈 배열은 현재 대상 미확인 |
| tracks | 트랙명 배열 또는 null | `[]`는 제한 없음, null/누락은 조건 미확인. 같은 뜻이 아님 |
| category | 관심 주제 ID | UI 카테고리와 별도 |
| noticeCategory / programCategory | 해당 유형 UI 분류 ID | 매핑 실패 시 미분류 |
| subtitle / benefit / department | 선택 문자열 | 없으면 원문 확인 또는 영역 생략 |
| preparations / tags | 선택 문자열 배열 | 실제 근거만 사용 |
| originalUrl | 게시물별 원문 HTTPS 주소 | 현재 프론트는 hansung.ac.kr 및 하위 도메인만 허용. 학교 CDN/새 공식 도메인은 합의 후 허용 규칙 수정 |
| images / imageUrls / imageUrl | 권장: images에 원문 순서의 HTTPS URL 또는 `{url,alt}` 배열. 단일/배열 URL 별칭도 지원 | 외부 로그인 없이 열려야 함. 실패 시 원문 안내. 현재 이미지 호스트 제한 목록은 없음 |
| publicInfo | 비교과의 공개 메타데이터 객체 | 다음 절 참고 |

현재 검증은 필수 형식 오류가 한 건이라도 있으면 전체 응답 교체를 거절하고 기존 목록을 유지합니다. 실패 상세를 반환하지만 네트워크 오류 UI·재시도는 호출부에 별도로 연결해야 합니다. null 응답, 오류 응답을 성공한 빈 목록 `[]`로 바꾸면 안 됩니다.

### 중요한 현 구조의 한계

1. **날짜 없는 공지:** 실제 공지에는 신청 기간이 없을 수 있지만 현재 경계는 start/deadline을 필수로 요구합니다. 날짜를 꾸며 넣지 말고, null 날짜·상시모집·모집 상태 미확인을 지원하는 모델과 화면을 연동 전에 추가해야 합니다. 단순 일반 공지와 모집 공지를 구분할지도 합의합니다.
2. **정확한 마감 시각:** 현재 D-day는 Asia/Seoul 날짜 기준입니다. 시작일 포함, 마감 당일 ‘오늘 마감’, 다음 날 ‘모집 마감’입니다. 18:00 마감처럼 시각이 있다면 ISO 타임스탬프와 정밀도(date/datetime)를 전달하고 프론트 상태 계산을 바꿉니다. 모르는 시간을 23:59로 생성하지 않습니다.
3. **페이지네이션:** 현재 ITEMS는 전체 목록 가정입니다. 페이지 한 장을 전체 교체하면 총 개수·MY PICK·추천이 틀립니다. 목록/필터 전체 개수, 다음 페이지, 북마크 목록·개별 상세 조회를 별도 설계해야 합니다.
4. **실제 공지 본문:** 현재 공지 상세는 요약·구조화 항목으로 구성되며, ‘공지 내용’은 그 값으로 재구성합니다. `bodyText`/문단·이미지 블록 같은 실제 본문 필드는 아직 없습니다. 본문을 읽게 하려면 서버 수집 필드와 프론트 렌더러를 추가합니다. 수집 HTML을 그대로 innerHTML에 넣지 않습니다.
5. **중복 정보:** 비교과 카드가 쓰는 상위 구조화 필드와 상세가 쓰는 publicInfo는 같은 출처 기준으로 일치시켜야 합니다. points만 보내면 현재 카드 benefit이 자동 생성되지는 않습니다. 실제 응답 매핑 단계가 필요합니다.

## 5. 비교과·이미지·AI 규칙

### 비교과

- 현재 프로젝트의 수집 범위는 비로그인 공개 목록입니다. 제한 경로/XHR/토큰 API로 빈 정보를 채우는 방식으로 확장하지 않습니다.
- `publicInfo`: summary, audience, applicationPeriod, points, department, location, format. 확인한 값만 전달합니다. points는 숫자 또는 숫자 문자열, 미확인은 null입니다.
- API 읽기 모델은 publicInfo가 없어도 `{}`로 정리합니다. 핵심 정보가 없으면 원문 확인, summary/location/format이 없으면 해당 소개·행을 생략합니다. 짧은 소개는 현재 최대180자로 표시합니다.
- 상세 본문이 없으면 제목만으로 준비물·목적·효과를 만들어 쓰지 않습니다. 공개된 기간·대상·pt·운영 부서 중심으로 안내합니다.

### 이미지

- [이미지 URL 연동 명세](image-url-integration.md): URL 응답 예시·필드 우선순위·표시/실패 처리·연결 위치. v1.16.76에서 단일 imageUrl/imageUrls 수신과 공지 내용 화면 표시를 보완했습니다.

- DB에는 이미지 URL과 대체 설명·원문 순서를 보관할 수 있습니다. 프론트 URL 표출·확대·실패 안내는 구현되어 있습니다.
- 원본의 외부 표출 차단·만료 URL이면 서버 보관/프록시 또는 안정적인 주소가 필요합니다. 서버에서 원격 이미지를 가져오는 경우에는 허용 호스트·주소 검증을 별도 적용합니다.
- 이미지 안에만 본문이 있는 경우, 이미지 표시와 AI 이미지 인식/OCR 요약은 별개 작업입니다. OCR/AI가 없으면 이미지를 보여주고 원문으로 안내합니다.

### 추천·AI 비교

- 현재 추천은 대상 조건 + 관심 분야 점수의 로컬 규칙이며 AI API 호출이 아닙니다. 비교도 2~3개 항목을 나란히 보여주는 UI입니다.
- 서버 추천/AI를 붙일 때 추천 대상·순위·이유·근거 출처·처리 실패/시간 초과 형식을 정합니다. 확인되지 않은 대상·혜택을 생성하지 않습니다.
- 서버가 준 일반 텍스트/AI 결과도 외부 입력입니다. 텍스트로 렌더링하고, 추가 HTML 허용이 필요하면 별도 정제 규칙을 적용합니다.

## 6. 추천·MY PICK 동작 정의

| 기능 | 현재 동작 | 서버/연동 시 유지할 것 |
|---|---|---|
| 기본 모집 필터 | 모집중 체크가 기본 | 체크 해제 시 마감/예정도 조회 가능 |
| 개인 추천 대상 | 학년 일치 AND 제한 트랙 중 하나 일치. 트랙 제한 없으면 학년만 확인 | 미확인을 제한 없음으로 처리하지 않기. 대학 선택과 하위 트랙의 계층 매칭은 별도 필요 |
| 개인 정보 없음 | 전체 모집중 탐색, 개인화라고 단정하지 않음 | 프로필 미입력 안내/입력 경로 |
| 추천 우선순위 | 관심 +100, 일치한 지정 트랙 +20, 특정 학년 +10, 이후 빠른 마감 | 서버 추천으로 교체할지 확정. 동점 정렬과 중복 제거도 동일하게 |
| 기타 학년 | 현재는 전 학년 공고만 개인 추천 | 기타를 4학년으로 바꾸는 것은 배너 표현뿐. 실제 대상 판정 정책은 합의 필요 |
| 마감 PICK | 모집중인 추천 대상 중 남은 날짜 0~3일 | 목록과 요약 숫자가 같은 조건 사용 |
| MY PICK 전체 | 북마크된 해당 유형만 표시 | 다른 사용자/미저장 항목 섞지 않기 |
| MY PICK 추천 | 북마크 ∩ 현재 추천 대상 | 저장했던 시점 추천이 아니라 현재 정보 기준. 모집 상태 필터는 별도 적용 |
| 저장 수와 목록 수 | 저장 수는 전체 저장, 기본 목록은 모집중만 | 숨겨진 마감/예정 항목 안내 유지 |
| 비교 | 공지/비교과 합쳐 최대3개, 최소2개 | 비교 완료 시 선택/팝업 해제, 북마크는 유지 |
| 추천 정보 재설정 | 기존 추천 정보는 새 입력 완료까지 유지, MY PICK 유지 | 프로필 수정과 계정 탈퇴를 구분 |

현재 이름 정규화는 ‘트랙’과 공백을 제거하는 수준입니다. 대학/학부→하위 트랙 계층 관계, 학교 트랙 개편 별칭은 자동 해결하지 못합니다. 서버에서 카탈로그 ID/계층/유효 연도를 정하고 프론트와 매핑해야 합니다.

## 7. 백엔드가 제공해야 할 기능·문서

아래는 **필요 기능 목록**입니다. 확정되지 않은 URL 경로를 만들어 계약하지 않았습니다.

| 기능 | 필요한 계약 |

| 가입/로그인 | 요청 필드·이름·중복 아이디·로그인 실패·가입 후 자동 로그인 여부 |
| 세션 조회/로그아웃 | 사용자 ID/이름·인증 수단, 만료·갱신·다른 기기 세션 정책 |
| 카카오/구글 | 시작·콜백 주소, 성공/취소/실패 복귀, 기존 계정 연결 충돌·해제 정책 |
| 찾기/비밀번호 변경 | 본인 확인 수단, 재설정 토큰/만료, 현재 비밀번호 확인, 소셜 전용 계정 처리 |
| 프로필 | 조회/수정·필수 트랙·이름·관심 분야·신규 계정의 프로필 미완성 상태 |
| 카탈로그 | 대학/학부학과/트랙 ID·표시명·부모 관계·개편/별칭·선택 가능 학년 |
| 목록/상세/추천 | 필터/검색/정렬/페이지네이션·총 개수·원문·본문/이미지·미확인 값 |
| 북마크 | 계정별 조회·저장·해제, 중복 저장 방지, 삭제/마감된 항목 처리 |
| 탈퇴 | 재인증·계정/프로필/북마크 처리 범위·완료/실패·로그아웃 |
| AI 기능 | 필요하다면 입력 제한·결과/근거·시간 초과·재시도·비용 제한 |

추가로 API base URL(개발/운영), OpenAPI/Swagger와 예제 JSON, 오류 code/message/fieldErrors, 테스트 계정, 프론트 도메인 허용 및 소셜 리디렉션 설정을 전달해 주세요. 테스트 계정 비밀번호/비밀 키를 공개 문서나 코드에 넣지 않습니다.

### 오류 응답에서 맞출 내용

- 입력 오류(400 또는422), 미인증/만료(401), 권한 없음(403), 없는/삭제된 항목(404), 중복 아이디/연결 충돌(409), 요청 제한(429), 서버 장애(5xx)를 구분합니다. 실제 코드 선택은 명세에서 확정합니다.
- 응답에는 사용자용 메시지와 안정적인 기계 판독 code, 필요 시 필드 오류·추적 ID를 제공합니다. 비밀번호·토큰·서버 스택을 노출하지 않습니다.
- 북마크는 ‘현재 상태 반전’ 요청보다 저장/해제의 목표 상태를 명시하는 동작을 권장합니다. 같은 요청을 반복해도 중복 레코드가 생기지 않도록 사용자ID+콘텐츠ID 유일성을 보장합니다.

## 8. 배포·인증에서 주의할 사항

현재 프론트 origin: `https://hsupick-campus-idea-contest.luckycrown8.chatgpt.site` (해시 경로는 origin에 포함되지 않음).

- 인증 방법(세션 쿠키/토큰)을 먼저 확정합니다. 계정별 접근 권한은 항상 서버에서 검증합니다. 프론트의 userId나 localStorage만 신뢰하지 않습니다.
- 쿠키 기반 교차 출처 요청이면 credentials·명시적 허용 origin·credentials 허용·OPTIONS 처리·CSRF·쿠키 속성을 함께 맞춥니다. credentials 요청에 허용 origin `*`를 쓰면 안 됩니다. 서로 다른 사이트의 쿠키는 브라우저 정책에 의해 차단될 수도 있으므로 CORS 허용만으로 로그인을 보장할 수 없습니다.
- 다른 사이트 도메인에서 쿠키 인증이 불안정하면 같은 origin의 API 프록시/BFF 또는 프론트·API의 도메인 구성을 함께 검토합니다. 현재 정적 호스팅에 서버 프록시가 구현되어 있다는 뜻은 아닙니다.
- 비밀번호는 검증된 비밀번호 해시(예: Argon2id)로 저장합니다. 카카오/구글 secret·AI 키·DB 접속 정보는 서버에서 관리합니다.
- 로그아웃/만료/계정 전환 시 계정별 메모리·캐시·미완료 요청·화면 기록을 분리합니다. 서버 응답이 늦게 와도 다음 사용자의 화면을 덮지 않게 해야 합니다.

참고한 공식/기술 자료:
- MDN CORS: https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS
- OWASP Password Storage: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html

## 9. 성진님과 먼저 결정할 미확정 정책

1. 이메일이 아닌 아이디를 쓰므로 **아이디 찾기/비밀번호 재설정의 본인 확인 수단**이 필요합니다. 현재 가입 화면은 이메일/전화번호를 수집하지 않습니다. 이메일·전화번호 추가, 소셜 재인증 등 가능한 방식을 정한 뒤 화면도 수정해야 합니다. 이름만으로 복구하지 않습니다.
2. 아이디의 대소문자 구분, 가입 후 자동 로그인, 기존 일반 계정과 소셜 계정 연결/충돌.
3. 로그인 없이 둘러보기를 유지할지. 로그인 필수로 결정되면 화면 진입 경로와 보호 API를 함께 정리합니다. 지금은 체험 경로가 남아 있습니다.
4. 날짜 없는 공지/상시모집/정확한 마감 시각, 모집중만 기본 필터에서의 포함 범위.
5. 학부/대학 선택의 추천 대상 계층 매칭, 기타 학년 대상 판정, 2학년 이상 1트랙의 대학 허용 여부.
6. AI 추천·비교를 실제 모델로 구현할 범위와 이번 배포에서 제외할 범위.
7. 게스트 프로필/북마크의 계정 이전 여부. 사용자의 선택 없이 계정 데이터를 덮어쓰거나 다른 사람 정보와 합치지 않습니다.
8. 탈퇴 시 삭제 범위/보관 정책과 화면 안내 일치, 삭제된 공지의 북마크를 남길지/안내할지.

## 10. 백엔드 구현 후 프론트에서 수정할 순서

| 순서 | 연결·수정할 부분 | 현재 코드/주의사항 | 완료 판단 |
|---|---|---|---|
| 1 | 공통 API 호출부 | base URL·인증·HTTP 오류·취소/시간 초과·중복 제출 방지. 아직 해당 계층 없음 | 느린/실패 응답과 로그아웃 후 늦은 응답을 처리 |
| 2 | 실제 인증·소셜·복구 | login.js의 준비 중 안내를 실제 요청/리디렉션으로 교체. 세션 확인 전 본문 노출 방지 | 새로고침·직접 링크·만료·취소에서도 정확한 화면 |
| 3 | 세션 전환·계정 데이터 주입 | account-session.js는 UI 어댑터일 뿐. 계정 ID 변경 시 기존 화면을 비우므로 새 계정의 프로필/북마크 주입 경로를 app.js에 추가 | A 계정 정보가 B 계정/비로그인 화면에 나타나지 않음 |
| 4 | 프로필·카탈로그·MY PICK | persist/toggleSave와 로컬 초기값을 서버 기반으로 교체. 게스트 이전 정책 적용 | 저장 성공 후 기기 간 재조회, 실패 시 상태 복구 |
| 5 | 실제 목록/상세/추천·개수 | data.js seed 의존을 줄이고 응답 매핑 후 읽기 모델 검증. 기간 없음/본문/페이지네이션 확장 | 총 개수·추천·북마크가 서버 전체 범위와 일치 |
| 6 | 상태·피드백 UI | 로딩·빈 결과·오류를 분리. 저장 처리 중·실패 재시도, 401 재로그인, 429 대기 안내 | 통신 실패가 빈 목록/저장 성공으로 보이지 않음 |
| 7 | 계정 관리·AI·정책 문구 | 실제 소셜 연결 상태/비밀번호 가능 여부·재설정·탈퇴, AI 결과 연결. 준비 중 문구 및 브라우저 초기화 정리 | 서버 처리 결과와 안내 문구가 일치 |
| 8 | 운영·실기기 통합 검증 | origin/소셜 callback/HTTPS·쿠키, 캐시 버전, 모바일/PC·인앱 브라우저 확인 | 아래 시나리오 통과 후 정식 공개 |

세션 확인 → 계정 ID 전환(기존 상태 정리) → 해당 계정 프로필/북마크 로드 및 주입 → 앱 진입의 순서가 필요합니다. 미리 fetch한 데이터를 쓰더라도 **주입은 ID 전환에 따른 정리 이후**에 해야 사라지지 않습니다. 데이터 로딩이 실패하면 별도 오류 화면/재시도를 제공하고 임의의 빈 프로필·북마크로 서버를 덮어쓰지 않습니다.

현재 호출 지점 예시(네트워크 기능 아님):

```js
import {replaceContentRecords} from './content-contract.js?v=1.16.75';
// 실제 요청의 HTTP 상태·현재 계정·요청 순서·응답 구조를 먼저 확인합니다.
const result = replaceContentRecords(mappedCompleteSnapshot);
// !result.ok이면 기존 목록을 유지하고 issues/retry UI를 호출부에서 표시합니다.
```

전체 스냅샷용 함수를 페이지 단위 갱신에 그대로 사용하지 않습니다. `setAccountSession`만 호출해서 로그인이 완료되거나 서버 저장이 연결된다고 가정하지 않습니다. 기존 browser storage에 서버 개인정보를 계속 혼합하지 않도록 계정 캐시와 게스트 값을 분리해야 합니다.

## 11. 연동 완료 후 반드시 통과할 시나리오

1. 신규 가입 → 로그인 → 이름/학년/트랙/관심 입력 → 추천 → 저장 → 새로고침 → 같은 계정 데이터 복원.
2. 1학년은 1트랙만, 그 외는 2트랙까지 필수. 중복/미등록 트랙 거절. 학년 변경 시 값 정리.
3. MY PICK 전체/추천·공지/비교과 전환. 마감 항목은 필터를 풀면 표시. 비교 완료 후 북마크는 유지.
4. 공지 이미지·없는 혜택·날짜 없음·상시모집·알 수 없는 분류·삭제된 상세·이미지 변경을 안전하게 안내.
5. A 계정 로그아웃 → B 로그인 → 브라우저 뒤/앞/새로고침. A 계정 데이터가 보이지 않음. 늦은 A 응답도 차단.
6. 401/403/404/409/429/5xx, 저장 중 연결 끊김, 중복 클릭, 늦은 검색 응답. 실패를 성공으로 처리하지 않음.
7. 카카오/구글 성공·취소·실패·기존 연결 충돌, 다른 기기 로그인, 비밀번호 변경·복구·탈퇴.
8. 한국 자정/정확한 마감 시각 전후, 휴대폰 절전 복귀, 서버 시간과 기기 시간 차이.
9. iPhone16급 화면·안드로이드·PC, 짧은 창·200% 글자 확대·키보드·고정 하단바·Back/Forward·원문 이동. 카카오 인앱 브라우저도 포함.

성진님이 제공할 1차 자료는 **API 명세 + 실제 JSON 예시 + 인증 방식/도메인 설정 + 테스트 계정 + 위 미확정 정책의 결정**입니다. 이 자료를 받은 뒤 프론트 어댑터와 실제 요청을 연결해야 통합 검증을 할 수 있습니다.
