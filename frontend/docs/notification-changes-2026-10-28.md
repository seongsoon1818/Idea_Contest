| `docs/notification-integration.md` | API 연결 방법, 발송 조건, 사용자별 구독 보안, 서버 구현/인수 검사 목록 |

## 3. 요청사항 → 구현 위치

| 요청 | 구현 |
|---|---|
| 같은 공지 마감 알림은 한 번 | 로컬 정책 `deadline:{noticeId}` 중복 키. 서버도 사용자별 고유 제약 필요 |
| 당일 마감까지 반복하지 않기 | 마감 전날만 대상. 당일 재발송 없음 |
| 맞춤 알림 하루 한 번 묶기 | 한국 시간 오전 9시 기준 하루 1건. 9시 이후 도착분은 다음 묶음 |
| 새로운 추천이 없으면 발송하지 않기 | 최초 목록을 기준으로 기록하고, 이후 새로 들어온 적격 소식만 모음 |
| 마감 알림 클릭 | 해당 상세 팝업. 대상이 삭제됐으면 안내 |
| 맞춤 알림 클릭 | 추천 목록 |
| MY PAGE 개별 설정 | 마감/맞춤 독립 스위치. 해당 종류 생성 중단, 기존 기록 유지 |
| 지난 알림 확인 | 상단 종 → 알림함, 최신순, 미읽음 점, 개별/모두 읽음 |
| 푸시 알림 | 수신 워커와 구독 UI/어댑터. 예약 발송 서버는 별도 연결 필요 |

## 4. 완료 범위와 남은 작업

### 프론트 포함
- 화면이 열린 동안 정책 평가 및 계정별 브라우저 기록 보존.
- `window.HSUPickNotifications.connect(adapter)` 연결 후 서버의 설정/기록 조회·변경.
- 브라우저 지원/권한 거절/서버 미연결/저장 실패 안내.
- 입력 데이터 HTML escape, 내부 경로만 푸시 이동, 이전 계정의 늦은 응답 배제.

### 백엔드에서 완료할 것
- 실제 로그인, 사용자별 프로필/MY PICK/설정/알림 DB 연결.
- 웹을 닫아도 실행되는 스케줄러 및 Web Push 발송.
- 원문 신청 마감일 검증, 발송 직전 저장 취소/설정/조기 마감 재검증.
- 같은 알림을 여러 번 만들지 않도록 DB 고유 제약/트랜잭션 적용.
- 로그아웃/탈퇴/공용 기기 계정 전환 시 푸시 구독 연결 해제.

푸시 수신 코드가 있다고 예약 발송 서버까지 완성된 것은 아닙니다. VAPID 공개키는 프론트에, 비밀키는 서버에만 둡니다.

## 5. 확인 방법

```bash
cd frontend
npm run check
cd dist
python3 -m http.server 8080
```

- `#notifications`에서 알림함, `#profile`에서 알림 설정 확인.
- 실제 알림이 없는 계정에는 빈 화면을 표시합니다. 가짜 알림을 운영 목록에 넣지 않았습니다.
- 검사 결과: PC/모바일 DOM 흐름 957개 및 알림 정책/서비스 워커 검사 통과.
- 실제 휴대폰 백그라운드 수신, 서버 인증/DB/구독 동기화는 백엔드 연결 후 추가 검증해야 합니다.
