## 1. 백엔드 자동 테스트 — MySQL 테스트 데이터

전체 **38개 중 35개 통과, 실패 집계 3개**. 직접 실패한 것은 공지 검색 `N01`과 비교과 검색 `P01` 두 건이고, 둘을 포함한 상위 테스트 한 건도 실패로 집계됐다.

| 화면 / API | 검색어 | 현재 결과 | 별도 복사본에서 쿼리 변경 후 |
|---|---|---|---|
| 공지사항 / `GET /api/v1/notices` | `교재` | 예상 항목 미노출 (`N01`에서 첫 실패) | 노출 |
| 공지사항 / `GET /api/v1/notices` | `출석`, `태그` | 예상 항목 미노출 (개별 확인) | 둘 다 노출 |
| 비교과프로그램 / `GET /api/v1/programs` | `직무탐색` | 예상 항목 미노출 (`P01`에서 첫 실패) | 노출 |

검색어가 포함된 값은 DB에 있었다. `status=all`로 모집 상태 필터를 풀어도 누락이 재현됐다. `N01`은 `교재`에서 멈추므로 `출석`, `태그`는 별도로 호출해 확인했다. 별도 복사본에서 검색식을 바꿨을 때 **위 네 검색어를 포함한 13개가 모두 통과**했다. 이는 수정 후보의 검색 검증 결과이며, 현재 GitHub 코드나 운영 반영 결과가 아니다.

**재현 방법:** `backend/`에서 `pnpm run test:e2e`를 실행한다. 테스트는 별도 MySQL 인스턴스를 띄우므로 로컬에서 `mysqld`를 실행할 수 있어야 한다. 실행 파일이 PATH에 없다면 `MYSQLD_BIN`으로 지정한다. API가 실행 중이고 해당 테스트 데이터가 준비된 환경이라면 아래처럼 직접 조회한다. HTTP 상태뿐 아니라 예상 공지·프로그램의 공개 ID가 응답 목록에 있는지도 확인한다.

```sh
curl --get 'http://127.0.0.1:3000/api/v1/notices' \
  --data-urlencode 'status=all' --data-urlencode 'q=교재'
curl --get 'http://127.0.0.1:3000/api/v1/programs' \
  --data-urlencode 'status=all' --data-urlencode 'q=직무탐색'
```

- **수정 위치:** `backend/src/notice/notice.index.ts`, `backend/src/program/program.index.ts`의 `search()`. 자동 테스트 위치는 `backend/test/notice-contract.mjs` (`N01`), `backend/test/program-contract.mjs` (`P01`).
- **확인한 단서:** JSON 배열을 직접 펼치면 검색 값이 읽혔지만, 현재 검색에 쓰이는 `EXISTS` 안의 `JSON_TABLE` 비교에서는 일치하지 않았다. 복사본에서는 `JSON_SEARCH`를 사용해 공지의 `benefits_json` 내 `text`·`condition`, 공지·비교과의 `tags_json` 경로만 검색했다. 이 방식은 수정 후보이며, 다른 환경에서도 원인이 같다고 단정하지 않는다.
- **수정 후 확인:** 위 네 검색어, 기존 제목·요약 검색, 영문 대소문자, `%`·`_`·이스케이프 문자, 공개되지 않은 데이터와 내부 메타데이터 제외, 모집 상태·분류·페이지네이션 및 결과 수를 확인한다. 이후 전체 E2E를 다시 실행한다.

## 2. 프론트–백엔드 계정 연동 — 로컬 실제 MySQL

프론트의 실제 요청 코드, Nest API, **MySQL 8.4 테스트 DB**를 연결했다. 아래는 계정 API와 DB 결과이며, 운영 DB나 공개 사이트에서 로그인 전체를 검증한 결과는 아니다.

| 항목 | 확인 방법과 결과 |
|---|---|
| 회원가입 | `POST /auth/signup` 성공 후 테스트 계정 행이 생성됐다. 한글 이름을 저장했고, 비밀번호 원문 대신 해시가 저장됐다. |
| 로그인 | 가입한 아이디·비밀번호로 `POST /auth/login` 성공. |
| 새로고침 상황에서 복원 | 새 프론트 클라이언트에서 기존 쿠키로 `POST /auth/refresh` → `GET /users/me` 호출. 갱신 쿠키가 바뀌고 동일한 계정이 복원됐다. |
| 로그아웃 | `POST /auth/logout` 이후 기존 세션으로 보호 API를 이용할 수 없었다. |
| 잘못된 입력 | 중복 아이디와 잘못된 비밀번호가 서버에서 거절됐다. 중복 아이디 오류의 화면 표시도 모의 API로 확인했다. |

표의 API 경로는 모두 `/api/v1` 아래에 있다. 프론트는 같은 출처에 요청하며, 쓰기 요청에는 `X-CSRF-Guard: 1`을 보낸다. 갱신 토큰은 서버가 설정하는 HttpOnly 쿠키로 관리하고, 액세스 토큰은 프론트 메모리에만 둔다.

**로컬에서 다시 확인:** `backend/.env.example`을 기준으로 테스트 DB, JWT 비밀값, 허용 출처 `http://127.0.0.1:8080`, 백엔드 포트 `3000`을 설정한다. `backend/`에서 빌드·테스트 DB 마이그레이션·카탈로그 시드를 마친 뒤 API를 실행하고, 계정 연동 프론트가 있는 체크아웃에서 `node frontend/scripts/local-auth-preview.mjs`를 실행한다. `http://127.0.0.1:8080`에 접속해 **회원가입 → 로그아웃 → 로그인 → 새로고침 → 로그아웃** 순서로 확인한다. 실제 브라우저에서 이 전 과정을 연속으로 완료하는 검증과 Windows 한글 키보드 조합 입력 검증은 남아 있다.

## 3. 기존 세션·연결 오류 보완 — 이번 GitHub 전달에 포함

| 상황 | 기존 문제 | 변경 후 / 검증 결과 |
|---|---|---|
| 같은 쿠키로 갱신 요청 두 건이 겹침 | 실제 DB에서 한 건 `200`, 한 건 `401`. 실패한 탭이 로그인 화면으로 돌아갔다. | 탭 간 잠금으로 갱신 순서를 맞춘다. 실제 DB에 연결한 두 프론트 클라이언트 모두 복원 성공 (`200`, `200`). 같은 탭의 중복 요청도 하나로 합쳤다. |
| 탭 간 잠금을 쓸 수 없는 환경 | 같은 충돌이 발생할 수 있다. | `401 INVALID_REFRESH_TOKEN`에만 간격을 두고 최대 세 번 재시도한다. 실제 DB 연동 테스트에서 충돌 `401` 이후 두 클라이언트 모두 복원됐다. |
| 오프라인·서버 장애·시간 초과 | 세션이 만료된 것처럼 로그인 화면이 열렸다. | 현재 주소를 유지하고 **다시 연결하기**를 표시한다. 복구하면 입력 없이 돌아간다. 오프라인, `503`, 사용자 정보 조회 시간 초과, 재시도 성공 및 중복 클릭을 프론트 화면 자동 테스트로 확인했다. |
| 세션 만료·로그아웃 | 다시 로그인해야 한다. | 실제 DB에서 만료된 쿠키와 로그아웃 이후 복원이 모두 거부됐다. 알려진 만료 응답 뒤 로그인 화면으로 돌아가는 것도 프론트 화면 자동 테스트로 확인했다. |

- **수정 위치:** `frontend/dist/account-api.js`(갱신 순서·재시도), `frontend/dist/login.js`(복원 상태 분기), `frontend/dist/index.html`·`styles.css`(재연결 UI), `frontend/tests/dom-flow.test.mjs`(회귀 검증). 사이트 소스에서는 동일 경로에서 `frontend/` 접두사가 없다.
- **검증 범위:** 배포 소스에서 `npm run check` 통과(화면 동작 단언 988개 포함). 두 탭 동시 새로고침은 실제 DB에 연결한 프론트 클라이언트로 검증했으며, 실제 브라우저 두 탭에서의 동시 새로고침은 미검증이다. 한 탭의 로그아웃을 다른 탭 화면에 즉시 반영하는 기능은 별도 후속 작업이다.
- **스테이징에서 재현:** 한 번 로그인 → 같은 주소를 두 탭에 열기 → 두 탭을 동시에 새로고침해 로그인 유지 확인 → 개발자 도구에서 오프라인으로 변경 후 열린 화면에서 세션 확인 요청이 실패하도록 테스트 → 온라인 전환 → 다시 연결하기 → 기존 화면 복귀 확인. 이어 한 탭에서 로그아웃한 뒤 다른 탭을 새로고침해 로그인 화면이 표시되는지 확인한다. 오프라인 새로고침 시 HTML 자체를 못 받으면 브라우저 오류가 뜰 수 있으므로, 그 경우 API 요청만 차단해 재연결 화면을 테스트한다.

## 4. 운영 연결 전에 확인할 것

| 우선순위 | 할 일 | 완료 기준 |
|---|---|---|
| 1 | **API 경로·운영 DB 연결** | 공개 데모에서 `GET /api/v1/home`이 `404`였고, 사이트 버전 94는 정적 데모 설정을 유지한다. 운영에서 프론트와 API를 같은 출처로 제공하고 `/api/v1/`을 백엔드로 전달한다. `ALLOWED_ORIGINS`에 정확한 운영 주소를 등록하고 HTTPS에서 쿠키 발급·갱신·삭제를 확인한 뒤 프론트 계정 API를 활성화한다. |
| 2 | **검색 수정 및 회귀 검증** | 위 누락 네 건이 조회되고 비공개 내용은 검색되지 않는다. 전체 E2E 재실행 결과를 공유한다. |
| 3 | **계정 외 화면 연동** | 공지·비교과 목록/상세, 프로필·추천, MY PICK, AI 비교, 알림 화면을 실제 응답으로 검증한다. 공지 이미지가 있는 경우 DB에 저장한 URL이 응답으로 내려오고 프론트에서 표시되는지 확인한다. 만료·빈 결과·이미지 실패도 확인한다. |
| 4 | **알림 형식 및 실기기 검증** | 아래 계약을 맞춘 뒤 브라우저 알림 표시, 클릭 경로, 알림함 읽음, 종류별 설정을 실제 기기에서 확인한다. |
| 5 | **시연 데이터 확인** | 기존 공개 데모 점검에서 기본 `모집중`으로 공지·비교과가 모두 0건이었다. 시연 전에 두 탭에 모집 중인 샘플을 준비하고, 추천 → 상세 → MY PICK 저장·해제를 실제로 눌러 확인한다. |

계정 API 활성화는 같은 출처에서 실제 API가 응답하는 환경에서만 진행한다. 기존 프론트는 로컬 주소에서 자동 활성화되며, 운영 빌드에서는 HTML에 `<meta name="hsupick-account-api" content="enabled">`를 넣어 활성화할 수 있다. **프론트 코드가 공개 사이트에 배포된 상태와 공개 사이트의 실제 계정 연동 완료는 별개**다.

### 알림 계약에서 맞출 부분

| 구분 | 현재 프론트 기대값 | 현재 백엔드 응답 |
|---|---|---|
| 웹 푸시 | `id`, `type: deadline/recommendation`, `itemId`, `title`, `body` | `notificationId`, `type: APPLICATION_DEADLINE_D1`, `contentRef: {type, id}`, `navigation: {screen, contentId}`, `title`, `body` 등 |
| 알림함 | 프론트 모델의 알림 유형과 `read` 여부 | 백엔드는 `APPLICATION_DEADLINE_D1`, `readAt`, `availability`, `contentRef`, `navigation` 등을 반환 |

- `frontend/dist/notification-sw.js`는 현재 타입이 다르면 푸시를 표시하지 않고, 마감 푸시를 `#notice/<id>`로만 보낸다. `backend/src/notification/notification.worker.ts`·`inbox.service.ts`와 기준을 맞춰 **공지와 비교과를 구분해 각각 해당 상세로 이동**시키고, 맞춤 알림은 추천 목록으로 보낸다. 알림함은 `readAt`을 읽음 표시와 연결하고 삭제되거나 비공개가 된 항목도 처리한다.
- **정책:** 저장한 공지의 마감 하루 전 한 번만 발송하고 당일 반복 발송은 하지 않는다. 새 추천이 있을 때만 하루 한 번 묶어서 보내고, MY PAGE에서 두 종류를 각각 켜고 끌 수 있게 한다. 테스트 DB에서 마감 예약 관련 자동 테스트가 통과했지만, 맞춤 묶음 발송은 점검한 백엔드에서 확인되지 않았다. 운영 테스트에서는 알림 중복, 설정 OFF, 클릭 이동을 따로 확인한다.

## 5. 이름 입력 제한 제안 — 미반영

- 안내 예시: **“본명을 입력해 주세요.”** 앞뒤 공백을 제거한 후 1~30자. 한글·영문·한자 등 모든 언어의 글자와 악센트를 허용한다. 이름 중간에는 공백, 하이픈(`-`), 아포스트로피(`'`, `’`), 가운뎃점(`·`)을 허용한다. 숫자, 이모지, 그 밖의 특수문자는 제외한다.
- 통과 예시: `이지원`, `Maria García`, `Nguyễn Thị Lan`, `O’Connor`. 거절 예시: `지원123`, `😊`, 공백만 입력. 프론트와 백엔드의 글자 수 계산과 허용 규칙을 동일하게 적용하고, 한글 조합 입력과 악센트가 포함된 이름을 실제 가입 화면에서 검사한다.
- 이 규칙으로 확인하는 것은 **이름의 형식**이다. 본명 사용 안내는 가능하지만, 형식 제한만으로 닉네임 입력을 막거나 본인·재학생 여부를 확인할 수 없다. 그런 검증이 필요한 경우 학교 계정 연동 등 별도 인증 정책을 정한다.
